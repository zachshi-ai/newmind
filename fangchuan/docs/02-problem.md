# 02 · 问题：Agent 吞错入码（运行期报错之口无账）

## 谁在什么场景下的什么问题

**谁**：用 agent 写代码并交付上库的工程师，以及排障的下一个会话/下一个人。

**场景**：agent 写代码时，为了「这单活不炸」，把运行期的报错之口一只一只堵上——
加载失败 `catch (e) {}`、校验异常 `except: pass`、网络失败 `.catch(() => null)`、
`catch { return; }`。测试是绿的（吞形不炸测试），任务宣告完成，代码上库。

**问题**：交付代码里的**吞错形**——错误从「报出来」变成「咽下去」：

- 异常状态静默累积：数据没加载、配置没读到、清理没执行，程序照跑，炸点在下游——
  排障时连「当时错没错、哪一行咽的」都无处问起；
- 人眼漏掉：吞形混在几百行 diff 里，比一行 `@ts-ignore` 更不起眼；
- 就算看见，也分不清是「best-effort 清理本该静默」还是「把该报的错咽了」——
  **意图无从考，词面可考而无人考**。

相邻层的空白地：乡校审**开发期**组织批评通道被静音（@ts-ignore/eslint-disable/it.skip
——写进文件的静音指令），运行期的错误通道不在其形表；直笔审**会话流内**命令记录被洗
（`|| true`），交付代码内容里的吞形不是记录；法仪审**验收器**（测试之尺的断言虚器），
器外的交付代码不归它；知行审**会话里**说了不做，代码里错了不言是另一条断层。

## 问题（治什么病）

四个病形，全部真实存在、全部有据可查：

| 病形 | 流内词面 | 现实对应 |
|------|----------|----------|
| **空捕** | `catch (e) { }` / `catch { }`（体剥空白为空） | AI 生成代码最经典的吞形——错误静默失踪 |
| **空还** | `catch (…) { return; }` | 以空返回抹掉失败，调用方拿到「成功」的假象 |
| **空接** | `.catch(() => null)` / `.catch(() => undefined)` / 空体箭头与空函数 | promise 链上的失败被抹成默认值——降级伪装成正常 |
| **空救** | `except …: pass`、多行空体 `except`、Ruby 空 `rescue` | Python/Ruby 侧的同一种堵口 |

价值锚点：每一处吞形都真实落在交付代码里，下一单活全数继承；对账材料全在会话流里
（write 的 `args.content` 就是末文的词面证据），词法可证；工具链侧 `no-empty` 类
lint 规则守仓库现状，但「**谁在何时写了吞形、后来改净了没有、任务方豁免了没有**」的
流内账，没有任何一层在记。本层不做语义判断（不判这次吞错值不值），只做词法判断
（在不在、几处、改净没有）——恰是零 LLM 能确定性回答的三问。

## 价值（为什么不是伪需求）

1. **每一笔都真实落在仓库里**：吞形是交付状态的既成事实，不是「可能有用」的推断；
2. **意图可豁免而词面须留痕**：best-effort 清理确实该静默——川册（任务方声明的纵列）
   开门即免案；无册之湮也不是罪，是**账**：留痕有价、点名有责、门禁有阈；
3. **账与闸分治**：不拦写（拦是 zhizhi 的地盘）、不改代码、不跑语义分析——扫描全部
   发生在流内词面上，观察永不反噬；
4. **可证伪**：湮形表、判定序、分数公式全部锁死于 03；同流重放必得同判词；
   跨项目历史流可验尸复算——错了改实现，不改标准。

## 产品形态

- **防川式插件**（DeepSeek Harness 插件层，Cordis，结构性零拦截）：挂 `tools/result`
  观察口，文账入账，导牌块接缝供给；
- **零依赖审计 CLI**（`fangchuan`）：多流离线重放，可验尸任何历史会话；
- **Agent Skill**：给派活方与 agent 的开川/导流协议。
