# 02 · 问题：Agent 变更膨胀

## 场景（谁在什么场景下）

**谁**：DeepSeek Harness 上跑的编码 Agent（以及一切「会话流可重放」的 LLM 编码代理）的**任务方与审计方**——需要 review Agent 交付的工程师、需要给 Agent 交付立门禁的 CI。

**场景一：小修大手术（巨写）。** 任务书写「修一下 login 的空指针」，Agent 一口气重写整个 auth 模块四百五十行：功能是对的（绿），但 review 面积扩大五十倍——reviewer 要么草草放行，要么把任务退回；无论哪种，损失都已发生。事后连「这一笔改了多少行、动的是新文件还是既有模块」都没有一笔账。

**场景二：写域扇出（蔓延）。** 「把配置项 timeout 改成可配置」，Agent 的手伸进八个目录：改代码、改测试、改文档、顺手统一命名——每一处单看都有道理，合起来没人能审。事后连「这次到底动了多少个地方」都没有一张表。

**场景三：改而不休（屡改）。** 同一个文件成功写入六次：改一版跑一次，不满意再改一版——每一版都覆盖上一版，最终态只有一个，但「这个文件今天被翻动过多少回」在流里无人记账。反复翻动的背后是同一件事：没有一版被真正想清楚。

## 问题（治什么病）

**Agent 变更膨胀**：会话流里每一次成功写入都真实落盘，但**没有任何一层审计变更的规模与广度**——

- 本仓 #1–#21 已交付的二十一层逐行核过登记表：知止拦危险动作（该不该做）、度支量投入花销（花了几笔）、有涯管读的重复（复见）、九变管失败的重复（盲捶）、终始记众事终始（走到没）、效验称成功成色（绿得实不实）——**「已经做的有多少、伸出去的手有多长」全仓无账**。
- 业界结构性证据：GitClear《AI Copilot Code Quality》2025 年度研究（1.53 亿行代码）：AI 编码助手主流化以来，短期 churn（返工）翻倍（3.3% → 7.1%），五行以上的重复代码块逐年上升，重构移动行占比从约 25%（2021）跌至不足 10%（2025）——**diff 在变大、返工在变多，而这正是 human review 成为瓶颈的时代**。

## 价值（为什么不是伪需求）

自检四问：

1. **问题是真实的吗？**——是。三场景都是 agent 编码的日常；GitClear 用 1.53 亿行代码度量出了趋势的结构性证据；「最小 diff」是所有主流 agent 使用指南的第一梯队纪律——但**只是纪律，没有账**。本仓的存在理由正是「原则会被违反，触发器不会」：把纪律变成逐案可点名的账。
2. **本仓二十一层真的没治吗？**——逐行核过方向登记表。最近似的几层：度支治**投入侧**（调用数/时长），本层治**产出侧**（写入行数/写域广度/同径翻动）；有涯管**读**的重复，本层管**写**的反复；九变管**失败**侧的重复，本层全在**成功**侧；定分裁**跨会话**写域归属，本层量**单会话**写域广度。谓词正交，边界在 docs/03 §11 逐层锁死。
3. **确定性可判吗？**——三宗全部是流内词法与计数：行数（真实换行切分）、目录扇出（规整径的去重 dirname）、同径写频（流序计数）。零 LLM、零语义判断、零网络、零子进程、零文件系统探测。
4. **判罪会不会冤枉？**——清白道全在设计里：创笔免记（新文件脚手架天经地义）、免额三笔（TDD 与渐进实现的合法迭代）、豁免径在册（任务方签发的生成物）、失败写不入案（未落盘、试错归九变）、exec 黑盒不判（写入体不可见，宁漏勿诬）、单屡改案十分不咬门（点名不门禁）。

## 产品形态

DeepSeek Harness **量出式插件**（Cordis，结构性零拦截）+ 零依赖审计 CLI + Agent Skill——与全仓范式一致：可运行、可测量、可证伪、可离线重放验尸。量出式是本实验室**第二十三个能力类型**（拦/审/供给/记习/诊/勘流/巡忆/守权界/封界/权界/秉笔/行前定/计账/审柄/记程/称实/核名/稽问/结绳/谏诤之后）：判定对象不是事件的性质，而是**事件的数量形——写了多少、散得多广、翻了几回**。
