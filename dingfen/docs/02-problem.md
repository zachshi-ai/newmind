# 02 · 问题：多会话并发争写——2026 年最日常的丢工作方式

## 谁，在什么场景下，遇到什么问题

**谁**：同时运行多个 Agent 会话的人与编排器——同一台机器上的几个终端、swarm 编排下的并行 worker、CI bot 与人并行、多个 Agent 在同一个 monorepo 上各领一个任务。

**场景**（2026 年的常态，不是假想）：一个仓库里，会话 A 在改 `core/auth.js`，会话 B 也在改 `core/auth.js`。三个层面的失败，按代价排序：

1. **争写**（有受害者，交错覆盖）：A 写了 `core/auth.js`，B 在 A 两次写之间也写了它，A 再写——B 的修改被无声覆盖。这是教科书 lost update 的 Agent 版：两只手交错地改同一个文件，谁都没看见对方的手。工作**真实丢失**，而且丢得无声——两个会话各自都"成功了"。
2. **侵入**（有受害者，闯入他方领地）：A 已经开工领了 `src/api/**`，B 直接闯进来改 `src/api/notes.md`，甚至"顺手清理"了 A 刚生成的文件。"不删对方成果"是并发协作的第一纪律——但纪律没有登记与对账机制时，它只能靠运气维持。
3. **越分**（暂无受害者，纪律失守）：B 声明了只写 `src/auth/**`，写着写着改了 `docs/plan.md`。没人被侵害，但权的边界失效了——下一次就越进别人的分里。
4. **（合法的对照）共写**：A 写完 `HANDOFF.md` 收工，B 接手再写。先后接手是协作的常态，**不计分**——定分止争，止的是"争"（交错），不是"共"（接续）。

**事后**：两个会话都报告成功，可工作区的状态是两者无意识合写的产物。谁在何时写了谁的地盘、哪一笔覆盖了哪一笔——连问都无处问起（势乱之道也）。

**这不是假想问题**：本仓库今天（2026-09-05）就有四个会话（buer / licheng / lunshi / youya）在同一工作区并行作业，操作协议里白纸黑字写着"不删对方成果、独立复验"——那份协议就是被真实事故逼出来的。仓库治理可以靠人的自觉，**编排器调度几十个并行 worker 的时候，靠什么？**

## 价值与意义

定分把"多会话并发协作"从纪律问题降为结构问题，三件事各有着落：

1. **事前止争**（卖兔满市）：开工领分，界碑块在接缝处公示权界与争界告警（附见证径）——第二只手开工前就知道哪里有分、哪里是自由地。
2. **事中门禁**（势治之道）：收工审争，争值对门——争写/侵入一票即红（+30 起），越分累犯至红；退出码可进 CI、可作编排器的准入裁决。
3. **事后归因**（置吏为师）：多流离线重放，逐字复现"谁在何时写了谁的地盘"——同一批流重放必得同一判词，审计不依赖任何人的记忆。

## 伪需求自检（为什么现有工具不够）

| 已有的东西 | 为什么不够 |
|---|---|
| `git` 的 `index.lock` | 瞬时互斥锁，防的是仓库元数据损坏；不登记领地、无归属、无账、跨会话无感知。 |
| 文件锁（fcntl / lockfile） | 运行时影子：锁存在时有效，进程死了就没了；无时间线、无重放、无权界语义（它是互斥，不是分封）。 |
| 编排器的任务分区 | 任务级 ≠ 路径级：两个任务共享 `src/` 时照样争写；且编排器只有任务账，没有可重放的路径账。 |
| `git merge` 冲突检测 | 提交（或合并）时才发现——token 已经烧完，覆盖已经发生；merge 只对已提交的行级冲突负责，对工作区内未提交的交错覆盖一无所知。 |
| "让模型自己小心" | 名分未定，尧舜且逐——纪律期望正是《商君书》点名要 replaced by 结构的东西；这也正是本实验室"原则会被违反，触发器不会"范式的第九次验证。 |

## 诚实边界（对应 docs/01 的四条，工程版）

1. 无分册不判越分（未领分的会话只有"未领分"提示，不计分）；
2. 侵入/越分只判显式 `p:` 路径对象，`c:`/`n:` 对象不判（命令黑盒）；
3. 争写需要全链时间戳，无时之流退出交错判定（记"无时"提示）；
4. 单会话的运行时视图里争写恒为 0（那是流间事实）——运行时只判侵入/越分，争写归离线多流审计。这不是缺陷是分工：每只手只看得见自己，所以需要置吏。
